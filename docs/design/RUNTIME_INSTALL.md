# CLI 运行时安装与更新

状态：2026-09-08 已实现 Web/Desktop 统一来源管理，四个 CLI 的 Linux 最新版安装、协议握手与卸载已验证。Agent CLI 不固定在桌面应用版本中，安装与启用为独立操作；Windows/macOS 实机验收仍待完成。

## 目标与可行性

在现有 Agent 管理页面按需安装缺失的 CLI、检查最新版、更新和卸载，无需重新构建或发布桌面应用。默认安装官方最新稳定版，不要求用户选择版本，也不以应用内硬编码的“已验证版本”白名单阻止下载。Pi、OpenCode、Codex 有 npm 分发；Grok 官方发布按版本与平台区分的二进制。

点击安装或更新时，解析官方最新稳定版及对应平台构件，并记录该次操作实际使用的版本、来源和完整性信息。解析后本次下载始终使用该构件，避免下载期间 latest 变化；这是安装记录，不是产品版本锁定。最新版没有当前平台构件时明确显示不可安装，不静默下载旧版或其他平台版本。预发布版本与任意历史版本选择不进入首版页面。

适配器实现仍随网关发布。新 CLI 必须通过版本与协议能力检查；缺少必需协议时标记不兼容，不启用或切换为当前运行版本，更新失败保留原来可用版本。未经过完整业务验收不能显示为“已验证”；安装最新版不承诺其上游协议一定向后兼容。

受管来源通过运行时清单解析四个 Agent 的绝对程序路径；用户个人 CLI 不参与更新，不写全局 npm、PATH 或 shell 启动文件。每个 Agent 在 settings.json 的 runtime 字段明确选择 managed 或 external。外部 CLI 检测实际文件和版本；切换前验证协议，切换失败恢复原来源、原生状态和会话绑定。

## 目录与状态

```text
AGENT_DATA_DIR/
  settings.json
  runtimes/
    codex/
      versions/<operation-id>/
      manifest.json
      staging/<operation-id>/
  agents/codex/
    config.toml
    sessions/<session-id>/
  backups/<agent>/<operation-id>/
```

settings.json 继续管理 Agent 配置和启用状态，不新增固定 CLI 目标版本。manifest.json 保存实际安装版本、来源、完整性信息、当前版本与必要的上一版本。最新版本查询结果包含查询时间，查询失败不把缓存标记为实时结果。清单是安装结果，不是另一套模型配置。安装任务、错误与日志需要持久化，网关重启后把中断安装标记失败并清理自己的临时目录。

三个状态分别表示：安装状态（未安装、安装中、已安装、卸载中、失败）、运行状态（停用、启动中、就绪、停止中、不可用）、更新状态（检查中、有更新、下载中、待切换、失败）。不把所有组合堆进同一个 status 枚举。查询最新版失败不影响已安装程序继续使用。

## 安装和更新流程

1. 从固定官方来源解析当前最新稳定版和平台构件，记录本次目标版本，校验平台、下载上限与可用磁盘空间。同一次动作内固定该构件；用户重试安装、更新或检查时重新解析 latest。
2. 下载或 npm 安装到 staging；验证分发完整性，执行版本命令和适配器协议握手。第三方任意 URL、包名和脚本不开放为管理接口。
3. 安装新版本时旧版本继续服务。切换前暂停新提交，处理排队项，等待活动执行结束；需要强停时使用现有明确操作。
4. 停止该 Agent 的原生进程后，备份其配置和全部原生状态；必须包含 SQLite WAL 等数据，不能复制仍在写入的单个数据库。
5. 原子更新当前版本清单，按当前管理配置启动新版本，验证会话恢复和就绪状态。失败时恢复上一版本及切换前状态，保留错误与日志。
6. 开放新提交后，不承诺任意时刻无损回滚：旧 CLI 可能无法读取新版本已写入的状态。此时恢复旧快照会丢失快照之后的原生上下文，必须明确处理，不能只更换可执行文件。

默认策略为进入“安装与版本”页签时检查最新版，也支持手动刷新；安装、更新和卸载由用户发起。不在每次启动或每次任务时自动升级，关闭各 CLI 自身自动更新。首版不提供通用版本管理器和历史版本选择；只保留切换失败恢复所需的上一版本及快照，清理不再需要的安装缓存。最新版本、已安装版本与当前运行版本分别记录，完整验收结果作为诊断信息。

## 卸载流程

1. 卸载仅针对 AgentBridge 管理的程序。按 Agent 串行处理安装、更新和卸载；卸载期间拒绝新提交并取消未开始的排队项，等待当前执行和审批结束，再停止引擎。用户需要立即中断时使用现有“立即停止”，不能静默杀掉活动任务。
2. 进程完全退出后，将该 Agent 置为停用，再删除其受管程序版本、安装缓存和仅供该程序恢复的备份。共享 Node、其他 Agent、共享 Skills/MCP 定义及用户个人 CLI 不删除；共用资源只有不再被引用时才能清理。
3. 保留模型设置、API Key、原生会话状态、任务历史和产物。删除失败显示具体错误，可重试且仍保持停用；全部程序删除完成后才标记未安装。重新安装最新版不自动启用，也不重放旧任务。

## 前后端调整

复用现有 Agent 列表和详情中的“安装与版本”页签，不新增一套导航或独立版本管理应用。页面显示平台、安装状态、已安装版本、最新版本及查询时间、磁盘占用、进度与失败原因。

| 状态 | 主要操作 |
| --- | --- |
| 未安装 | 安装最新版 |
| 已安装且有更新 | 更新到最新版、卸载 |
| 已安装且已是最新版 | 检查更新、卸载 |
| 安装或更新中 | 查看进度、取消；切换阶段按原子操作完成，不在中途强行取消 |
| 下载失败或不兼容 | 查看原因、重试或重新检查；有旧版本时继续保留旧版本 |
| 卸载中或卸载失败 | 查看进度或重试；完成前保持停用 |

运行中的 CLI 可继续服务于更新下载阶段，切换和卸载阶段复用现有 Agent 生命周期约束；其他 Agent 不受影响。安装不隐式启用，停用不卸载。更新失败自动恢复属于错误处理，不新增必须由用户选择历史版本的流程。

后端复用进程管理、超时、错误脱敏与现有 Agent 操作编排。CLI 分发使用固定的四项描述，不建立插件市场、通用安装脚本引擎或动态适配器加载系统。每次 Run 额外记录实际 CLI 版本，以便定位更新前后差异。

## 已实现接口与分发

- `GET /api/runtimes`：返回四个运行包视图。
- `POST /api/runtimes/:id/actions`：`{ action: "check" | "install" | "update" | "uninstall" | "cancel" }`，返回 202；按 Agent 串行执行，页面轮询当前状态。
- `AGENT_MANAGED_RUNTIMES=false` 仅在首次初始化时选择外部来源；默认受管；`AGENT_RUNTIME_NODE`、`AGENT_RUNTIME_NPM` 分别指定实际 Node 与 npm-cli.js，桌面自动设置。两种入口使用相同管理 API。外部来源禁止直接更新或卸载，可先准备受管安装再显式切换。
- npm 使用官方 registry、完整性锁与 `--ignore-scripts`；Pi 同时安装 MCP 所需依赖。OpenCode 使用匹配平台的独立二进制包，避免 wrapper 复制。
- Grok 使用官方 GCS stable 与固定 generation，校验 HTTPS 返回的 MD5 和长度；MD5 不是签名认证。
- 每个 Run 持久化实际 `runtimeVersion`；无法取得版本时为空；历史数据库不兼容，不提供迁移。
- npm 进度不可精确计算时显示忙碌状态；Grok 提供下载字节进度。npm staging 每 500ms 检查 2GiB 上限，不提供硬磁盘配额。

## 实际限制

- 握手只验证协议入口；切换到“已验证”版本还需工具调用、交互回复、中断与恢复测试。
- Grok 官方安装脚本会写个人目录、配置和 shell；受管模式应直接下载官方构件。
- npm 包可能有安装脚本及平台二进制依赖，需要复用包管理器与锁定的分发来源。
- Windows 文件占用、杀进程和原子目录切换须实机验证；安装过程不覆盖正在运行的文件。
- 无网络时仍能使用已安装版本。下载凭据与模型 API Key 分离，不引入模型 login 流程。

## 验收重点

覆盖首次安装最新版、查询结果过期、下载中 latest 变化、无对应平台构件、网络中断/重试/取消、完整性失败、协议不兼容保留旧版、运行中更新与卸载、删除失败重试、离线使用，以及卸载保留配置和历史、重装不重放任务。实际下载到的 CLI 版本见 [真实安装记录](../../code/artifacts/desktop/runtime-install-smoke.json)；离线失败/取消/切换回滚/卸载保留数据由自动测试覆盖，四个官方 CLI 另做真实安装、握手和卸载。协议检查不代表所有模型与工具行为均已验收。
