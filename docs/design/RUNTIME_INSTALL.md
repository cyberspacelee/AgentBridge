# CLI 运行时安装与更新建议

状态：方案分析，尚未纳入当前实现。动态启停与配置应用已经属于本次开发；动态下载安装是另一个生命周期，不能把启用等同于安装。

## 目标与可行性

网关运行期间可安装缺失的 Agent CLI、检查更新、安装指定版本、切换与回滚，无需重新构建或部署前端。Pi、OpenCode、Codex 有 npm 分发；Grok 官方发布按版本与平台区分的二进制，并支持指定版本下载。适配器实现仍随网关发布，不能因 CLI 有新版就宣称新协议已兼容。

当前 Pi/OpenCode 由项目 package.json 固定，Codex/Grok 依赖主机命令。受管安装落地后，四个 Agent 都改为通过运行时清单解析绝对可执行路径；用户个人 CLI 不参与更新，不写全局 npm、PATH 或 shell 启动文件。

## 目录与状态

```text
AGENT_DATA_DIR/
  settings.json
  runtimes/
    codex/
      versions/<exact-version>/
      manifest.json
      staging/<operation-id>/
  agents/codex/
    config.toml
    sessions/<session-id>/
  backups/<agent>/<operation-id>/
```

settings.json 保存目标版本及更新策略；manifest.json 保存实际安装版本、来源、完整性信息、当前版本与上一版本。清单是安装结果，不是另一套模型配置。安装任务、错误与日志需要持久化，网关重启后把中断安装标记失败并清理自己的临时目录。

三个状态分别表示：安装状态（未安装、安装中、已安装、失败）、运行状态（停用、启动中、就绪、停止中、不可用）、更新状态（检查中、有更新、下载中、待切换、失败）。不把所有组合堆进同一个 status 枚举。

## 安装和更新流程

1. 从固定官方来源解析精确版本和平台构件，校验版本、平台、下载上限与可用磁盘空间。
2. 下载或 npm 安装到 staging；验证分发完整性，执行版本命令和适配器协议握手。第三方任意 URL、包名和脚本不开放为管理接口。
3. 安装新版本时旧版本继续服务。切换前暂停新提交，处理排队项，等待活动执行结束；需要强停时使用现有明确操作。
4. 停止该 Agent 的原生进程后，备份其配置和全部原生状态；必须包含 SQLite WAL 等数据，不能复制仍在写入的单个数据库。
5. 原子更新当前版本清单，按当前管理配置启动新版本，验证会话恢复和就绪状态。失败时恢复上一版本及切换前状态，保留错误与日志。
6. 开放新提交后，不承诺任意时刻无损回滚：旧 CLI 可能无法读取新版本已写入的状态。此时恢复旧快照会丢失快照之后的原生上下文，必须明确处理，不能只更换可执行文件。

默认策略为自动检查、手动安装和切换；关闭各 CLI 自身自动更新。自动更新可在后续明确运维要求下支持，但仍必须限定经适配器验证的版本范围。最新版本、已安装版本、当前运行版本和已验证版本分别显示。

## 前后端调整

复用 Agent 详情增加“安装与版本”页签：平台、当前版本、可用更新、版本选择、安装/更新/回滚、进度与失败重试。安装与运行操作按 Agent 互斥；其他 Agent 不受影响。安装不隐式启用，停用不卸载，卸载仅删除受管程序版本，保留配置和任务历史。

后端复用进程管理、超时、错误脱敏与现有 Agent 操作编排。CLI 分发使用固定的四项描述，不建立插件市场、通用安装脚本引擎或动态适配器加载系统。每次 Run 额外记录实际 CLI 版本，以便定位更新前后差异。

## 实际限制

- 握手只验证协议入口；切换到“已验证”版本还需工具调用、交互回复、中断与恢复测试。
- Grok 官方安装脚本会写个人目录、配置和 shell；受管模式应直接下载官方构件。
- npm 包可能有安装脚本及平台二进制依赖，需要复用包管理器与锁定的分发来源。
- Windows 文件占用、杀进程和原子目录切换须实机验证；安装过程不覆盖正在运行的文件。
- 无网络时仍能使用已安装版本。下载凭据与模型 API Key 分离，不引入模型 login 流程。
